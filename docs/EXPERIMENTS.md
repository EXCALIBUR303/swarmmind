## Calibration (Phase 3)

**Method** (§20.6): for each level, evaluate the Random policy and the
greedy nearest-frontier reference heuristic on that level's frozen
**validation** set (50 procedurally generated maps, seeds
1,000,000–1,000,049). `max_steps(level) = round_up_to_10(3 × P90(heuristic
completion steps))`, bounded below by the provisional value chosen in
Phase 0/1 if that is larger. Random success on L2 must stay below 0.6 or
the level needs adjusting (§20.6); the heuristic's success rate must reach
≥ 0.95 within the resulting `max_steps` or the level/heuristic needs
revisiting.

**Result: every level's Phase 0/1 provisional `max_steps` already exceeds
what the calibration formula requires, so no level's `max_steps` changed.**
The provisional values become each level's calibrated value, to be frozen
as-is in Phase 6.

| Level | `max_steps` (unchanged) | Heuristic P90 steps | Formula floor (3×P90, rounded up to 10) | Heuristic success | Random success | Random censored-mean steps |
|---|---|---|---|---|---|---|
| L1 | 100 | 17.1 | 60 | **1.000** | 0.58 | 71.48 |
| L2 | 150 | 21.0 | 70 | **1.000** | 0.54 | 116.58 |
| L3 | 200 | 28.2 | 90 | **1.000** | 0.38 | 167.90 |
| L4 | 200 | 60.0 | 180 | **1.000** | 0.26 | 180.06 |

(50 validation-map episodes per cell, 1 episode/map, evaluation sampling
seed derived per-map; generated by `scripts/evaluate.py --split validation`.)

**Gate checks:**
- Heuristic success ≥ 0.95 at every level within its `max_steps`: **PASS** (all 1.000).
- Random success on L2 < 0.6: **PASS** (0.54).
- No level required a density/target-count adjustment.

**A note on reproducibility:** the first calibration pass used Python's
built-in `hash()` to derive per-episode evaluation seeds in
`scripts/evaluate.py`, which is randomized per-process (`PYTHONHASHSEED`)
and produced different Random-policy numbers on every run — a
reproducibility bug in the *script*, not the environment. Fixed by
deriving seeds from `sha256` instead; the table above reflects the fixed,
now-stable numbers (confirmed identical across repeated runs).

**A note on the heuristic itself:** the first calibration pass surfaced two
genuine bugs in the reference heuristic (fixed in this phase, see
`docs/phase_reports/PHASE_3.md`): (1) two robots' independent plans could
permanently deadlock by repeatedly targeting the same destination cell,
and (2) a robot's plan could target a cell a *different*, not-yet-processed
robot still physically occupied, which the environment's own R1 rule
always blocks regardless of what that occupant does — producing the same
kind of permanent standoff. Both are fixed by resolving each robot's
ranked candidate list sequentially against a set of already-claimed/
currently-occupied destination cells, plus a light anti-backtrack
tie-break to prevent 2-step oscillations. These fixes are internal
bookkeeping for a hand-coded reference tool (§14.2) and do not touch the
environment's own symmetric, index-independent conflict rule (§6.5), which
is unchanged.

## Map-generator bug and evaluation-set contamination (found in Phase 5)

**What happened.** `mapgen._hash64` (the per-attempt seed derivation)
computed `np.uint64 % int`, which NumPy 1.x evaluates in float64. The 64-bit
word was rounded to a multiple of 2048 before the modulo, zeroing the low 11
bits of every attempt seed — so each level had only ~2^20 (~1M) distinct
procedural maps instead of ~2^31. That alone barely affects training
diversity (~30k maps per run), but it made the §20.3 isolation failure
concrete: collisions with the 150 frozen L1 eval maps were expected at
~30k × 150 / 2^20 ≈ 4 per run. Compounding it, the in-training isolation
guard (reject any training map whose hash is in a frozen eval set) had
been designed in Phase 3 but never wired into training.

**Exact impact** (replaying each run's seed streams up to the final
generator state saved in its checkpoint — `scripts/audit_eval_isolation.py`
for the upper bound, exact counts via generator-state matching):

| Runs (study `l1_gate`, mapgen v1) | Training maps used / seed | Frozen eval maps trained on |
|---|---|---|
| IPPO L1 seeds 0/1/2 (Phase 4 gate) | 30,438 / 29,091 / 29,066 | 4 / 1 / 3 (4 validation + 4 test in total, each seen once) |
| MAPPO L1 seeds 0/1/2 (first Phase 5 run) | 30,776 / 28,826 / 28,956 | same 8 maps (IPPO and MAPPO share seed streams) |

**Fix (Phase 5).** (1) `_hash64` does the modulo in exact integer
arithmetic (`MAPGEN_VERSION = 2`, recorded in every generated map's
metadata; regression test asserts near-zero collisions and non-zero low
bits). (2) The trainer now passes the union of every level's frozen
validation+test hashes to the vector env, which redraws on any hit and
records `training_maps_rejected_as_eval` in the run manifest.

**What stays valid.** The frozen validation/test sets are immutable data
loaded from JSON; they were generated by v1 but are still valid, reachable,
disjoint sets (their recorded `seed` just no longer regenerates them under
v2 — do not regenerate; `make_eval_maps.py` now refuses to overwrite
without `--force`). The Phase 3 calibration numbers were computed on these
exact files and are unaffected. The contaminated `l1_gate` runs are kept
on disk as a superseded record; the Phase 4 and Phase 5 gate evidence is
re-run cleanly as study `l1_gate_v2` (mapgen v2 + guard).

### 2. Statistics (spec §4, §22.2)

- **Unit of analysis: the seed.** Each learned run contributes the mean of each metric over its held-out episodes; Random contributes one number per evaluation sampling seed. Episodes are never treated as independent samples.
- Per arm: mean, sample SD, 95% t-interval (reported as computed; not clipped to a metric's range).
- Differences: mean difference with a **Welch** 95% CI and Welch's two-sided p, plus Hedges' g. If both arms have zero variance the CI is *undefined* and no inference is drawn.
- No multiplicity correction is applied; each hypothesis is reported separately with its CI. With n = 5 per arm the power is low: a CI that includes 0 is reported as "no detectable difference", never as equivalence.
- Sample efficiency: normalized area under the validation-success curve, trapezoid rule over the **first 245,760 env steps** (D3; spec default was the whole budget — see §6).
- **Decision rules** (implemented mechanically in `marl/analysis/aggregate.py`, tested in `tests/evaluation/test_aggregate.py`):
  - **H1** (per learned algorithm): supported iff the Welch 95% CI of (learned − Random) test success, stochastic, final checkpoint, excludes 0 on the positive side.
  - **H2**: supported iff the Welch 95% CI of (MAPPO − IPPO) on **censored steps-to-completion** (D1; spec default was test success — see §6) excludes 0; direction and Hedges' g reported either way. Secondary, reported but not decisive: test success and the validation AUC.
  - **H3**: evaluated in Phase 8 (DER@50, §24); no coordination claim before then.
  - **H4** (descriptive): per-seed retention = structured success / test success, mean with t-interval; seeds with zero test success are excluded and counted.
  - **H5**: stretch only (`scale_L3` vs `comm_L4`); not part of this pre-registration.

### 3. Deviations policy

- After freezing, no design file may change. A needed change is run with `--allow-deviation`, which records it in `results/studies/main_L2/study_manifest.json`, and it is reported in RESULTS.md and the Phase 7 report.
- A run that fails is resumed from its last checkpoint. A run that cannot finish is reported as missing — **never replaced by a new seed** and never dropped silently.
- No tuning on test results. Any Phase 7 sanity-check failure stops the study for review (§38, Phase 7).

### 6. Decisions (approved 2026-09-24)

The user approved all four recommendations as-is. `configs/experiments/main_L2.yaml` was updated accordingly (`total_env_steps: 1000000`, `analysis: {h2_primary_metric: censored_steps, auc_window_env_steps: 245760}`), then frozen.

**D1 — H2 decision metric: censored steps-to-completion** (not test success rate).
- *Reason:* on L2 both algorithms hit 1.00 validation success by 82k steps. At the final checkpoint both will almost surely score about 1.00 on test, with near-zero variance. Welch's CI is then undefined or trivially includes 0, so H2 on success cannot come out any way except "no detectable difference". The research question (§3.1) asks which is *more efficient*, and §3.2 names steps-to-completion as one of its pre-registered measures. Success stays H1's metric and is still reported for H2, as a secondary.
- This is a deviation from the Phase 0 spec text, made before any study data exists and based only on the validation-only pilot.

**D2 — training budget per run: 1,000,000 env steps** (not the spec's 3,000,000).
- *Reason:* the pilot's L2 curves are flat from about 125k. 1M is 8× that point, leaving margin for slower seeds and late instability without spending two-thirds of the compute on a plateau. About 5.5 h wall time for the 10 runs, vs. ~17 h at 3M.

**D3 — sample-efficiency (AUC) window: the first 245,760 env steps** (not the whole budget).
- *Reason:* all learning on L2 happens in the first ~125k steps. A whole-budget AUC would be about 0.99 for both algorithms at any budget and could not show a difference.

**D4 — primary level: L2, unchanged.**
- *Reason:* L2 and L3 saturate on success; L4 (no communication) is still learning at 250k. D1–D3 make L2 informative despite saturating on success, so the study answers the question the spec asked. L4 is deferred to the `comm_L4` stretch study (unfrozen; needs its own budget pilot before it can run), since it is the most likely place for IPPO and MAPPO to actually differ.
